# Auto-Compounder Vault for veMEZO Rewards: Security Architecture & Implementation

## 1. Executive Summary

The Auto-Compounder Vault automates veMEZO position management on the Mezo network, holding users' veMEZO NFTs and executing compounding strategies via an off-chain keeper bot. This document provides a comprehensive security analysis covering the entire attack surface—smart contract vulnerabilities, off-chain automation risks, economic attack vectors, and operational security. The analysis draws on established smart contract security best practices, documented DeFi security incidents from 2025–2026, and the specific security characteristics of the Mezo protocol stack.

## 2. Security Landscape: The Mezo Protocol Foundation

### 2.1 Protocol-Level Security

Mezo has undergone extensive independent security audits across its entire protocol stack. Halborn conducted two separate reviews of the core Cosmos-based codebase, including a "clean room" assessment. OtterSec examined bridging logic and validator infrastructure, focusing on attack surfaces around BTC tokenization and validator consensus. Spearbit/Cantina analyzed MUSD, covering refinancing logic, liquidation mechanisms, and overall system design. Quantstamp and Thesis Defense independently audited Mezo Passport, the system of contracts for Mezo accounts for both Bitcoin and EVM wallets. Cantina's open competition model surfaced a wide range of submissions, allowing deeper visibility across the stack beyond what a single audit firm could provide.

According to Gate.io's project analysis, Mezo has undergone nine independent security audits covering application contracts, chain client (mezod), MUSD stablecoin, cross-chain bridges, and the Mezo Earn system. CertiK Skynet data indicates three completed third-party audits, with auditors including QuantStamp and Thesis Defense, and a composite security score of 78.41 (BBB rating).

### 2.2 Implications for the Auto-Compounder Vault

The underlying protocol's security posture provides a strong foundation for the vault, but the vault introduces additional attack surface beyond the base protocol:

- **Custodial Responsibility**: The vault holds users' veMEZO NFTs, creating a new trust assumption that does not exist in the base protocol
- **Keeper Bot Infrastructure**: The automation layer introduces off-chain components with elevated privileges
- **Integration Complexity**: Interacting with veMEZO, GaugeController, and MUSD contracts creates cross-contract vulnerability pathways

The 2026 DeFi security landscape demonstrates that even audited protocols remain vulnerable. 90% of exploited contracts in 2024 had been previously audited. Recent incidents such as the Drift Protocol $285M governance-layer attack (April 2026), the Yearn $9M invariant solver exploit (November 2025), and the GMX $42M keeper vulnerability (July 2025) confirm that security must be treated as a continuous, multi-layered process rather than a point-in-time assessment.

## 3. Smart Contract Security Architecture

### 3.1 Core Vulnerability Classes and Mitigations

#### 3.1.1 Reentrancy Attacks

Reentrancy remains one of the most devastating vulnerability classes in smart contracts, responsible for the DAO hack, the Balancer exploit ($121M loss), and countless other incidents. The vault must implement defense-in-depth against reentrancy across multiple dimensions.

**Primary Defense: OpenZeppelin ReentrancyGuard**

```solidity
import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract VeMEZOAutoCompounder is ReentrancyGuard {
    function deposit(uint256 tokenId) external nonReentrant {
        // Implementation
    }
    
    function withdraw(uint256 tokenId) external nonReentrant {
        // Implementation
    }
    
    function compoundAll() external onlyKeeper nonReentrant {
        // Implementation
    }
}
```

OpenZeppelin's ReentrancyGuard uses a mutex (lock) mechanism that prevents reentrant calls. However, one critical limitation must be observed: functions marked as `nonReentrant` cannot call other functions with the same modifier, as this will cause a revert and potentially create a denial-of-service condition.

**Secondary Defense: Checks-Effects-Interactions Pattern**

Every state-changing function must strictly follow the Checks-Effects-Interactions (CEI) pattern:

```solidity
function _compound(uint256 tokenId) internal returns (uint256 totalRewards) {
    // ========== CHECKS ==========
    require(nftOwner[tokenId] != address(0), "Token not deposited");
    
    // ========== EFFECTS ==========
    // All state updates must occur BEFORE external calls
    uint256 pendingRebase = veMEZO.calculatePendingRebase(tokenId);
    uint256 pendingIncentives = gaugeController.calculatePendingRewards(tokenId);
    totalRewards = pendingRebase + pendingIncentives;
    
    // Update user share accounting BEFORE external interactions
    _updateUserShare(nftOwner[tokenId], totalRewards, true);
    
    // ========== INTERACTIONS ==========
    // External calls occur only after all state changes are complete
    uint256 claimedRebase = veMEZO.claimRebase(tokenId);
    uint256 claimedIncentives = gaugeController.claimRewards(tokenId);
    
    // Additional external calls for swap and re-lock
}
```

This pattern prevents reentrancy attacks by ensuring that even if an external contract calls back into the vault, the state has already been updated to reflect the intended outcome.

**Cross-Function and Cross-Contract Reentrancy**: Beyond single-function reentrancy, the vault must protect against complex reentrancy paths that span multiple functions or contracts. The interaction with veMEZO's `safeTransferFrom` during deposit, which can trigger `onERC721Received` callbacks, creates a potential reentrancy vector that must be explicitly accounted for.

#### 3.1.2 Access Control Vulnerabilities

Access control failures are among the most common causes of DeFi exploits. The vault has several privileged functions that require granular access control.

**Keeper Authorization**:

```solidity
modifier onlyKeeper() {
    require(msg.sender == keeper, "VeMEZOAutoCompounder: caller is not keeper");
    _;
}

function updateKeeper(address newKeeper) external onlyOwner {
    require(newKeeper != address(0), "Invalid address");
    address oldKeeper = keeper;
    keeper = newKeeper;
    emit KeeperUpdated(oldKeeper, newKeeper);
}
```

**Two-Step Ownership Transfer**:

Standard `Ownable` contracts are vulnerable to ownership transfer errors. Using OpenZeppelin's `Ownable2Step` mitigates the risk of accidentally transferring ownership to an invalid or inaccessible address:

```solidity
import "@openzeppelin/contracts/access/Ownable2Step.sol";

contract VeMEZOAutoCompounder is Ownable2Step, ReentrancyGuard {
    // Two-step ownership transfer requires explicit acceptance by new owner
}
```

**Performance Fee Management**:

```solidity
uint256 public performanceFee = 1000; // 10% (basis points)
uint256 public constant MAX_PERFORMANCE_FEE = 2000; // 20% cap

function setPerformanceFee(uint256 newFee) external onlyOwner {
    require(newFee <= MAX_PERFORMANCE_FEE, "Fee exceeds maximum");
    uint256 oldFee = performanceFee;
    performanceFee = newFee;
    emit PerformanceFeeUpdated(oldFee, newFee);
}
```

**Critical Privilege Audit**:

All privileged functions must have proper access control guards. The vault should maintain a clear privilege matrix:

| Function | Access Control | Justification |
|----------|---------------|---------------|
| `compoundAll()` | `onlyKeeper` | Automation-only, prevents unauthorized compounding |
| `emergencyPause()` | `onlyOwner` | Emergency response capability |
| `setPerformanceFee()` | `onlyOwner` | Economic parameter adjustment |
| `updateKeeper()` | `onlyOwner` | Keeper rotation for security |
| `withdraw()` | `nftOwner` check | Self-custody guarantee |
| `deposit()` | Public | Open access |

#### 3.1.3 Arithmetic Safety

Solidity 0.8.0+ includes built-in overflow and underflow protection, eliminating the need for SafeMath in most cases. However, several arithmetic vulnerabilities persist even in modern Solidity.

**Division Before Multiplication**: This pattern causes precision loss:

```solidity
// VULNERABLE: Precision loss
uint256 fee = amount / 10000 * performanceFee;

// SECURE: Multiply before division
uint256 fee = (amount * performanceFee) / 10000;
```

**Unchecked Blocks**: Only use `unchecked` when arithmetic overflow is provably impossible:

```solidity
function _removeTokenId(uint256 tokenId) internal {
    for (uint256 i = 0; i < depositedTokenIds.length;) {
        if (depositedTokenIds[i] == tokenId) {
            depositedTokenIds[i] = depositedTokenIds[depositedTokenIds.length - 1];
            depositedTokenIds.pop();
            break;
        }
        unchecked { ++i; } // Safe because loop bounds are controlled
    }
}
```

**Fee-on-Transfer Token Compatibility**: If reward tokens include fee-on-transfer mechanisms, the vault must account for the discrepancy between the `transfer` amount and the actual received amount. The current implementation assumes standard ERC-20 behavior; this assumption should be documented and verified.

#### 3.1.4 Oracle and Price Manipulation

The compounding logic may require price feeds for swapping reward tokens to MEZO. Oracle vulnerabilities represent a significant attack vector.

**Security Requirements**:

- Never use AMM spot prices for critical calculations (vulnerable to single-block manipulation)
- Use time-weighted average price (TWAP) for all price-sensitive operations
- Implement staleness checks with maximum allowed age (e.g., 1 hour)
- Include circuit breaker logic for oracle downtime or anomalous deviations

```solidity
interface IPriceOracle {
    function getMEZOPrice(address token) external view returns (uint256 price, uint256 updatedAt);
}

function _swapForMezo(address token, uint256 amount) internal returns (uint256) {
    (uint256 price, uint256 updatedAt) = priceOracle.getMEZOPrice(token);
    require(block.timestamp - updatedAt <= 1 hours, "Stale price");
    require(price > 0, "Invalid price");
    // Execute swap with slippage protection
}
```

#### 3.1.5 Denial of Service (DoS) Vectors

**Unbounded Loop Attacks**: The `depositedTokenIds` array can grow arbitrarily large. An attacker could deposit many minimal-value NFTs, causing the `compoundAll()` function to exceed block gas limits:

```solidity
// VULNERABLE: Unbounded iteration
function compoundAll() external onlyKeeper {
    for (uint256 i = 0; i < depositedTokenIds.length; i++) {
        _compound(depositedTokenIds[i]); // Gas cost grows linearly
    }
}
```

**Mitigation Strategies**:

1. **Batch Processing with Pagination**:

```solidity
function compoundBatch(uint256 startIndex, uint256 batchSize) external onlyKeeper {
    uint256 endIndex = startIndex + batchSize;
    if (endIndex > depositedTokenIds.length) endIndex = depositedTokenIds.length;
    
    for (uint256 i = startIndex; i < endIndex;) {
        _compound(depositedTokenIds[i]);
        unchecked { ++i; }
    }
}
```

2. **Minimum Deposit Threshold**: Prevent dust attacks by requiring meaningful deposits:

```solidity
uint256 public constant MIN_DEPOSIT_VALUE = 1e18; // 1 MEZO equivalent

function deposit(uint256 tokenId) external nonReentrant {
    uint256 nftValue = veMEZO.balanceOfNFT(tokenId);
    require(nftValue >= MIN_DEPOSIT_VALUE, "Deposit too small");
    // ...
}
```

3. **Incentive-Aligned Compounding**: The keeper bot should prioritize positions with highest reward-to-gas ratios, making dust attacks economically irrational.

**Pull-over-Push Pattern**: For reward distributions, always use pull-based withdrawal rather than pushing funds to users:

```solidity
// VULNERABLE: Push pattern
function distributeRewards() external {
    for (uint256 i = 0; i < users.length; i++) {
        (bool success, ) = users[i].call{value: reward}("");
        // Single failed transfer blocks all subsequent distributions
    }
}

// SECURE: Pull pattern
mapping(address => uint256) public pendingRewards;

function claimRewards() external nonReentrant {
    uint256 amount = pendingRewards[msg.sender];
    require(amount > 0, "No rewards");
    pendingRewards[msg.sender] = 0;
    mezoToken.safeTransfer(msg.sender, amount);
}
```

### 3.2 Token Interaction Security

#### 3.2.1 SafeERC20 Implementation

All token interactions must use OpenZeppelin's SafeERC20 library, which provides safety checks for operations like `transfer` and `approve`:

```solidity
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";

contract VeMEZOAutoCompounder {
    using SafeERC20 for IERC20;
    
    function _compound(uint256 tokenId) internal {

    }

```

**Non-Standard Token Compatibility**: Some ERC-20 tokens (e.g., USDT, USDC on certain chains) do not return a boolean from `transfer`/`transferFrom`. SafeERC20 handles these edge cases correctly.

#### 3.2.2 ERC-721 Receiver Implementation

The vault must properly implement `IERC721Receiver` to accept veMEZO NFT deposits:

```solidity
function onERC721Received(
    address operator,
    address from,
    uint256 tokenId,
    bytes calldata data
) external override returns (bytes4) {
    // Only accept NFTs from the veMEZO contract
    require(msg.sender == address(veMEZO), "Only veMEZO NFTs accepted");
    return this.onERC721Received.selector;
}
```

**Reentrancy Warning**: The `onERC721Received` callback executes during the `safeTransferFrom` call. Any state changes that depend on the transfer completion must account for this execution order.

### 3.3 Upgradeability Security

The current vault design is non-upgradeable, which eliminates upgrade-related vulnerabilities but also removes the ability to patch bugs. If future versions require upgradeability, the following security measures are essential:

- `_disableInitializers()` called in implementation constructor
- Upgrade function behind timelock and multi-sig (minimum 5-of-9)
- Transparent upgrade pattern with clear separation between proxy and implementation

## 4. Off-Chain Security: The Keeper Bot Attack Surface

### 4.1 The Automation Layer as a Critical Vulnerability

The 2025 GMX $42M exploit fundamentally changed how the DeFi industry views automation security. The attack was not a smart contract vulnerability—it was a surgical strike against GMX's off-chain keeper infrastructure, where a malicious contract reentered the vault mid-execution before state updates completed.

What GMX calls a "keeper," other protocols call relayers, automation bots, or off-chain agents. They all share the same property: they hold the keys to write to a chain on the protocol's behalf. The auto-compounder vault's keeper bot falls into this exact category—a privileged off-chain component with authorization to execute state-changing transactions on user funds.

Security must be treated holistically: "Treat these as first-class security surfaces: onchain code (contracts, libraries, upgrade modules), offchain services that influence state (keepers, relayers, oracle pipelines, automation), backend and auth flows, deployment and ops code, and frontend transaction construction."

### 4.2 Keeper Bot Threat Model

The keeper bot faces multiple distinct threat vectors:

| Threat | Attack Vector | Impact | Mitigation |
|--------|--------------|--------|------------|
| Private key compromise | Key exfiltration from environment | Complete vault control | Hardware security module, environment isolation |
| Transaction manipulation | Malicious transaction injection | Unauthorized fund movement | Transaction simulation before submission |
| Gas griefing | Excessive gas consumption | Profit erosion | Gas price caps, profitability checks |
| RPC manipulation | Malicious RPC responses | Incorrect execution decisions | Multiple RPC sources with consensus |
| DOS on keeper | Resource exhaustion | Missed compounding | Redundant keeper deployment |
| MEV extraction | Sandwich attacks on swaps | Reduced yield | Private mempool submission |

### 4.3 Keeper Bot Security Implementation

**Private Key Management**:

The keeper's private key must never be hardcoded and should be stored with multiple layers of protection:

```javascript
// DO NOT: Hardcoded key
const PRIVATE_KEY = "0x1234..."; // Critical security violation

// DO: Environment variable with encryption
const PRIVATE_KEY = process.env.KEEPER_PRIVATE_KEY;
if (!PRIVATE_KEY) {
    throw new Error("KEEPER_PRIVATE_KEY environment variable required");
}
```

For production, consider using OpenZeppelin Defender Relayers, which provide secure key management without exposing private keys to application code.

**Transaction Simulation**:

Before submitting any transaction, the keeper should simulate it to validate expected outcomes:

```javascript
async function simulateCompound(vault, tokenIds) {
    try {
        // Simulate the transaction locally
        const simulation = await vault.compoundAll.staticCall();
        
        // Validate that the expected rewards are claimable
        const expectedRewards = simulation.totalRewards;
        const gasEstimate = await vault.compoundAll.estimateGas();
        const gasCost = gasEstimate * gasPrice;
        
        // Only proceed if profitable
        return expectedRewards > gasCost * 1.1; // 10% minimum profit margin
    } catch (error) {
        logger.error("Simulation failed", { error: error.message });
        return false;
    }
}
```

**Gas Price Protection**:

```javascript
const MAX_GAS_PRICE = ethers.parseUnits('100', 'gwei'); // Configurable cap

async function checkGasPrice(provider) {
    const feeData = await provider.getFeeData();
    if (feeData.gasPrice > MAX_GAS_PRICE) {
        logger.warn("Gas price exceeds maximum", {
            current: ethers.formatUnits(feeData.gasPrice, 'gwei'),
            max: ethers.formatUnits(MAX_GAS_PRICE, 'gwei')
        });
        return false;
    }
    return true;
}
```

**Redundant Keeper Deployment**:

Single-keeper architectures create a single point of failure. The vault should support multiple keepers or use decentralized automation networks:

- **Chainlink Automation**: Decentralized keeper network with reputation system
- **Gelato Network**: Web3 automation with fallback mechanisms
- **OpenZeppelin Defender**: Managed relayer infrastructure

```solidity
// Support for multiple authorized keepers
mapping(address => bool) public authorizedKeepers;

modifier onlyKeeper() {
    require(authorizedKeepers[msg.sender], "Not authorized keeper");
    _;
}

function addKeeper(address newKeeper) external onlyOwner {
    authorizedKeepers[newKeeper] = true;
```

### 4.4 MEV and Front-Running Protection

The compounding transaction involves swapping rewards for MEZO, creating a MEV opportunity. Sandwich attacks can extract value from the swap, reducing compound yield.

**Mitigation Strategies**:

1. **Private Mempool Submission**: Use Flashbots or similar services to submit transactions directly to block builders, bypassing the public mempool
2. **Slippage Protection**: Include minimum output amount checks in swap transactions
3. **Time-Distributed Execution**: Spread compounding across multiple smaller transactions to reduce MEV visibility

## 5. Economic Security and Attack Vectors

### 5.1 Flash Loan Attack Analysis

Flash loans enable attackers to temporarily acquire large amounts of capital, potentially manipulating the vault's share accounting or price feeds.

**Vulnerability Assessment**:

- **Share Manipulation**: An attacker could deposit a large veMEZO position, trigger compounding, and immediately withdraw, capturing a disproportionate share of rewards
- **Price Oracle Manipulation**: If swaps use AMM spot prices, flash loans could manipulate the exchange rate to extract value

**Mitigations**:

1. **Deposit Lock Period**: Require minimum deposit duration (e.g., 1 epoch) before withdrawal
2. **Share Calculation Based on Time-Weighted Value**: Use block.timestamp-weighted average rather than instantaneous snapshots
3. **Minimum Deposit Value**: Prevent dust attacks as described in Section 3.1.5

```solidity
struct Deposit {
    uint256 tokenId;
    uint256 timestamp;
    uint256 initialValue;
}

mapping(uint256 => Deposit) public deposits;

function withdraw(uint256 tokenId) external nonReentrant {
    Deposit memory dep = deposits[tokenId];
    require(dep.timestamp + MIN_DEPOSIT_DURATION <= block.timestamp, "Lock period active");
    // ...
}
```

### 5.2 Governance Attack Surface

The vault interacts with Mezo's governance system through veMEZO voting. An attacker controlling a large veMEZO position could potentially influence gauge incentives to benefit malicious strategies.

**Risk Mitigation**: The vault should maintain a neutral voting policy, delegating voting decisions to a governance-controlled multisig rather than allowing arbitrary keeper-directed votes. The keeper bot should focus exclusively on claiming rewards, not directing votes.

### 5.3 Fee Collection and Economic Sustainability

The 10% performance fee model must balance protocol sustainability with user incentives. Improper fee calculation can create economic exploits:

```solidity
function _compound(uint256 tokenId) internal returns (uint256 totalRewards) {
    uint256 rebaseAmount = veMEZO.claimRebase(tokenId);
    uint256 incentiveAmount = gaugeController.claimRewards(tokenId);
    totalRewards = rebaseAmount + incentiveAmount;
    
    // Critical: Fee calculated on gross rewards BEFORE compounding
    uint256 fee = (totalRewards * performanceFee) / 10000;
    
    // Fee collected from rewards, not from user principal
    // This ensures users always receive net positive value from compounding
}
```

## 6. Integration-Specific Security Considerations

### 6.1 veMEZO NFT Custody and Transfer Safety

veMEZO NFTs are soulbound to the wallet that created them—they cannot be transferred directly between users. The vault acts as a custodian, creating a critical security dependency:

- **Custody Guarantee**: Users must be able to withdraw their exact veMEZO NFT at any time
- **Accounting Integrity**: The vault's internal share accounting must never diverge from the actual veMEZO positions held
- **No Rehypothecation**: The vault must not lend out or otherwise encumber users' veMEZO positions

### 6.2 MUSD Integration Security

MUSD integration for fee collection adds another token interaction surface. Security considerations include:

- **MUSD Contract Verification**: Confirm the MUSD contract address matches the official deployment
- **Stablecoin Depeg Risk**: In extreme market conditions, MUSD may deviate from its $1 peg, affecting fee value
- **Fee Conversion Timing**: If fees are collected in MEZO and converted to MUSD, the timing of conversion can impact protocol revenue

### 6.3 Mezo Passport Security

The frontend integration with Mezo Passport must maintain secure wallet connection patterns:

- **Signature Verification**: All transactions must be signed by the user's wallet, not delegated to the frontend
- **Network Validation**: Verify the connected wallet is on the correct Mezo network (chainId 31611 for testnet)
- **Phishing Protection**: The frontend should display clear domain information and transaction details before signature

### 6.4 Cross-Chain Considerations

Mezo's bridging infrastructure (built on tBTC v2, the most decentralized Bitcoin bridge with over 21k BTC bridged since 2020) provides the underlying security for BTC movement. The vault does not directly interact with bridges, but users depositing veMEZO may have bridged their assets from Bitcoin. Bridge security is therefore a transitive dependency.

## 8. Testing and Verification Strategy

Minimum testing requirements for security validation:

- **Unit Tests**: 100% coverage of all functions, including edge cases
- **Fuzz Testing**: Automated property-based testing for arithmetic operations and state transitions
- **Fork Testing**: Deploy against Mezo testnet fork to validate real-world behavior
- **Invariant Testing**: Define and verify system invariants (e.g., sum of user shares always equals total underlying)

The Auto-Compounder Vault for veMEZO Rewards presents a moderate-to-high security complexity due to its custody of user NFTs, integration with multiple protocol contracts, and reliance on off-chain automation. The security architecture outlined in this document provides defense-in-depth across all attack surfaces:

| Security Layer | Primary Controls | Residual Risk |
